They're already doing work. They just haven't been named, measured, or improved — until now.

## The Analogy: A Schema Is a Seed that Spawns a Factory

Here's the concept that crystallized while building the scanner:

**A schema is a seed. It contains a factory blueprint, not a finished product.**

Think about it. A sunflower seed isn't a sunflower. It's:
- **Structure** — the outer shell (the schema definition itself)
- **Instructions** — encoded DNA telling the plant what to build (the field definitions, validation rules, required fields)
- **Nutrients** — starter energy for germination (default values, initial state)
- **Timing** — when to sprout, when to flower (lifecycle stage, maturity indicators)
- **Self-correction** — the plant grows toward light, away from shade (the feedback loop)

When the seed is planted:

**Step 1: Germination** — the seed cracks open. The schema is loaded. L0 identity (name, version, maturity) is read first. No other content is fetched. This is progressive disclosure at the cellular level.

**Step 2: Root deployment** — the factory begins constructing its control plane. The schema defines what agents the factory can create, what tools they can use, what signals they must emit. This is determined by the schema itself — not by any external orchestrator. The control plane is predetermined by the DNA.

**Step 3: Stem growth** — the factory executes its reconcile loop. It scans for existing instances, validates them, scores them, evolves them. This is the controller pattern from Part 1 — the factory observing its own output.

**Step 4: Branching** — the factory discovers new patterns through signals. An option in a menu is selected 3x in a row. The factory notices. It promotes that option. A task gets deferred and never resurfaces. The factory notices. It adjusts the defer rules. This is signals as control — telemetry driving decisions, not just recording them.

**Step 5: Flowering** — the factory produces new seeds. Templates are updated. Skills are created. New schemas are proposed. Each seed carries the same DNA structure but with different field values — the same factory blueprint with different parameter values.

**Step 6: Self-correction** — the factory audits its own output. The schema scanner (the mirror) runs weekly. It checks: "Am I healthy? Are my fields duplicated? Are my consumers declared? Is my changelog current?" This is recursiveness — the system applies to itself.

The seed doesn't grow into a tree — it grows into the machine that makes trees. And the machine improves itself by measuring its own output.

## Where This Avoids Overengineering

The risk with schema-heavy architectures is becoming a bureaucracy of forms — every change requires approval, every field must be registered, every modification needs a committee. This is schema management as paperwork. That's not what we're building.

The schema-as-seed metaphor prevents this because **a seed doesn't need management.** It contains everything it needs to produce its factory. The factory manages the output. The output feeds signals back to the factory. The factory adjusts. That's one loop, not ten committees.

Three design choices that prevent overengineering:

### 1. Progressive Disclosure Means Schemas Load Lightly

A schema doesn't load its full definition upfront. L0 (identity) is 50 tokens. L1 (purpose and scope) is 300. L2 (commands and configs) is 2,000. Most interactions never reach L4 (full reference). This means the schema infrastructure doesn't consume context budget just by existing. You pay for what you use.

### 2. Signals Replace Manual Auditing

Instead of a human reviewing every schema change, signals tell the system what's working. If a field is never selected, it gets flagged. If a menu option is always chosen first, it stays. If a defer rule consistently fails to resurface, it gets rewritten. The system audits itself through usage patterns, not through paperwork.

### 3. The Factory Pattern is Emergent, Not Imposed

The factories (skill-factory, research-factory, project-factory) already exist. They were not designed to fit a schema model — the schema model was extracted from how they already work. This is taxonomy, not engineering. We're naming what exists and making it explicit, not forcing existing systems into an abstract framework.

## What "Evolving Complexity Without Overengineering" Actually Means

It means: **complexity emerges from simple rules, not from complex designs.**

The simple rules:
- Every schema declares what it is (L0)
- Every schema declares what it extends and mixins (composition)
- Every schema declares who uses it (consumers)
- Every action emits a signal
- Signals accumulate and influence future behavior
- Templates absorb proven patterns
- Schemas audit themselves periodically

That's it. Six rules. No committees. No approval boards. No bureaucracy.

But applied recursively, those six rules produce:
- Self-improving menus (signals → reordering → better selections)
- Self-correcting tasks (outcome data → classification improvements → better task creation)
- Self-documenting schemas (changelog → scanner → health score → fix → changelog)
- Self-evolving templates (signal patterns → template updates → better instantiation)
- Self-referencing systems (tasks about tasks, schemas about schemas, signals about signals)

The complexity emerges. You don't design it into the architecture. You design a simple rule set and let the recursion compound.

**The difference between evolution and engineering is that evolution compounds while engineering accumulates.** Engineering adds features one at a time. Evolution multiplies the effect of each change across every layer simultaneously. An engineered system has N features. An evolved system has N effects from each of N features on each of N layers. That's N squared.

## Conclusions

### About What Exists

The schema ecosystem is functional but undocumented. Ten schemas, 59/100 health score, six areas with real work ahead. Not a disaster — a starting point. The fact that the system works at all without formal schema governance is evidence that the emergent pattern is sound. Formalization will make it faster, not different.

### About What's Coming

The unified task-schema will replace five separate task-like structures. The defer state machine will replace a flat list with contextual resurfacing. The schema scanner will run weekly, not on demand. Health scores will trend upward. Templates will evolve automatically. Factories will improve themselves.

### About the Analogy

The seed-to-factory metaphor isn't just poetry. It's an accurate description of what's happening:

- The schema **contains** the factory blueprint (DNA)
- The factory **executes** the control plane (protein synthesis)
- The signals **guide** the factory's next actions (phototropism)
- The templates **preserve** what works (seed production)
- The progressive disclosure **manages** resource allocation (cellular differentiation)
- The recursion **compounds** improvement across generations (adaptation)

A seed doesn't overengineer the tree. It specifies the rules, releases the structure, and lets natural selection handle the rest. The schema ecosystem should do the same.

Phase 2: create base-entity, mixins, and the unified task-schema. Add `$`-metadata to all 10 schemas. Register all consumers. Start changelogging. Run the scanner weekly. Watch the health score climb from 59 to 90.

Phase 3: connect the feedback loop. Let signal data drive template evolution. Let task outcome signals improve task classification. Let defer abandonment patterns improve defer rules.

Phase 4-5: formalize progressive disclosure and autonomous schema evolution.

But all of that starts with the baseline: **we know what we have now.** And knowing is the first form of control.
